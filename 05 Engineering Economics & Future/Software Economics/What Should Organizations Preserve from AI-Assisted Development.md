# What Should Organizations Preserve from AI-Assisted Development

When coding agents make the marginal cost of generating syntax negligible, treating raw source code as the primary intellectual property of an engineering organization is a mistake. Code is an ephemeral downstream artifact—it can be refactored, generated, or rewritten on demand. What an organization cannot afford to lose is the upstream intent and the downstream verification: why an architectural choice was made, which domain invariants must hold, which alternative paths were tried and rejected, and the deterministic test suites that prove the system works.

If your domain specifications, decision records, and test suites survive, an agent can re-synthesize the implementation details overnight. If you lose the context and verification boundaries, you are left with legacy code that neither humans nor models can safely modify.

```text
       DISPOSABLE ARTIFACTS                      DURABLE INTELLECTUAL PROPERTY
+---------------------------------+      +-----------------------------------------+
| - Ephemeral code syntax         |      | - Architectural Decision Records (ADRs) |
| - Boilerplate and glue code     | ---> | - Business Decision Records (BDRs)      |
| - Scratchpad generation logs    |      | - Rejected trade-offs and dissents      |
| (Freely refactored and replaced)|      | - Deterministic test suites and schemas |
+---------------------------------+      +-----------------------------------------+
```

## Documentation Can Become a Process Output

Maintaining accurate business and architectural documentation has historically failed because it requires high-friction manual labor that drifts from the codebase over time. Agents alter this dynamic by turning documentation into a low-cost byproduct of the development loop, helping safeguard [[LLM Agents and Institutional Memory|institutional memory in software teams]].

For every feature or refactor, an agent can extract and maintain:

- Domain documentation and ubiquitous language glossaries.
- Business Decision Records (BDRs).
- Architectural Decision Records (ADRs).
- Decision tables for complex branching logic.
- Inline rationale near non-obvious business rules.
- Traceability links connecting requirements, test cases, and code changes.
- Migration paths and schema evolution notes.
- Operational boundaries and known edge-case limitations.

Because [[Why Business Logic Is the Hardest Part of Agentic Coding|business logic is the hardest part of agentic coding]], documenting business decisions explicitly prevents future models from guessing at critical business rules. A practical Business Decision Record looks like this:

```markdown
# BDR-XXX: Decision title

## Context
What ambiguity or business problem existed?

## Decision
How should the system behave?

## Examples
What is allowed and rejected?

## Rationale
Why was this behavior selected?

## Consequences
What systems, processes, or data does it affect?

## References
Code, tests, tickets, and previous decisions.
```

The human engineer's role shifts from writing these records from a blank page to verifying their factual correctness, embedding them directly into [[In-Flight Documentation as the Primary Framework for Coding Agents|in-flight documentation for coding agents]]. 

When generating documentation, the agent harness must strictly distinguish between three classes of information:

1. **Confirmed facts**: Explicit rules sourced directly from verified specifications or human instructions.
2. **Inferred conclusions**: Behavioral patterns deduced from inspecting the existing code paths.
3. **Assumptions requiring validation**: Speculative logic that lacks test coverage or explicit documentation.

Under no circumstances should an agent be permitted to invent plausible-sounding historical rationale. If the code does not reveal *why* a workaround exists, the record must flag it as an open question rather than halluncinating intent.

## Agent Work Data Becomes Strategic Intellectual Property

The long-term value generated by engineering teams is not just the clean diff that merges into `main`. The true strategic value lies in the complete reasoning trajectory:

```text
task
→ repository analysis
→ proposed plan
→ agent attempts
→ compiler and test failures
→ human review
→ corrections
→ accepted diff
→ production outcome
```

This trajectory captures operational knowledge that traditional repositories discard:

- How the team evaluates trade-offs and reaches consensus.
- Which architectural patterns were evaluated and thrown out.
- The implicit business rules that only surfaced when an automated test failed.
- Which implementations survived production scale and network partitions.
- How senior engineers spot subtle concurrency bugs or security anti-patterns during review.

Organizations should treat agent execution traces, PR review discussions, rejected patches, test runs, and post-deployment metrics as proprietary training data and institutional context, rather than ephemeral CI/CD logs.

### Negative Trajectories and Rejection Logs

When teams assemble datasets to fine-tune internal models or build retrieval-augmented context for their agents, they almost always collect only successful outcomes: merged pull requests, green test runs, and polished source files.

This creates severe survivorship bias. Clean source code only shows the destination; it erases every minefield the team navigated to get there.

The most defensible organizational training data lives in negative trajectories:

1. **Rejected Implementation Attempts**: The candidate architectures generated by the model that failed static analysis, violated memory footprints, or introduced deadlocks under concurrent access.
2. **Human Code Review Dissents**: The exact rationale a senior engineer provides when rejecting syntactically valid code—such as unindexed queries that choke at production scale, subtle violations of domain invariants, or abstractions that break cache locality.
3. **Debug Trajectories and Flaky Test Isolation**: The exact diagnostic path an agent followed when resolving a distributed race condition or edge-case state bug before landing on the minimal fix.

As discussed in [[Negative Knowledge and Explicit Architectural Dissents]], training or prompting exclusively on positive examples produces brittle models that confidently wander into the same well-known architectural dead ends. Storing and indexing negative trajectories turns your historical failures into an active defensive perimeter for future runs.

## Training on Model-Generated Code Requires External Verification

As model-generated code proliferates across public and private codebases, future models will increasingly ingest synthetic code during pre-training and fine-tuning.

Unchecked training on raw synthetic output creates autophagous feedback loops:

- Compounding common stylistic and architectural anti-patterns.
- Drastically reducing structural and algorithmic diversity.
- Stripping out rare, highly optimized domain-specific tricks in favor of common web idioms.
- Prematurely converging on whatever framework design is currently fashionable in public repositories.

Model-generated code is only useful as training material when it has been vetted against objective, external reality:

- Clean compilation under strict type checking.
- Passing unit, integration, and property-based test suites.
- High mutation testing scores (proving the tests actually detect behavioral changes).
- Performance benchmarks and memory profiling under load.
- Static analysis and security linters.
- Human review catching subtle architectural drift.
- Real-world production telemetry and post-incident maintenance records.

The high-value training asset is never raw generated code by itself. The actual unit of value is:

> **Generated proposal + external verification proving its correctness.**

## Practical Working Rules

### For Documentation and Architecture

- **Keep decisions co-located with code**: Store BDRs, ADRs, and schema specs in the same repository as the implementation so they branch, merge, and stay in sync together.
- **Generate drafts as a standard pipeline step**: Have your coding agents draft or update BDRs and ADRs as a required artifact of any non-trivial pull request.
- **Enforce explicit cross-references**: Require direct links connecting decisions, test cases, implementation files, and tracking tickets.
- **Separate fact from inference**: Force agents to clearly demarcate confirmed requirements from inferred patterns and unverified assumptions.
- **Atomic updates**: Update documentation, domain specifications, and automated tests in the very same diff that alters system behavior. Never defer documentation to a follow-up ticket.
