# AI May Replace Some Source Generators with Explicit Generated Code

## Core Thesis

For decades, software engineering relied on metaprogramming—runtime reflection, compile-time macros, annotation processors, and custom source generators—to solve a human problem: **writing and maintaining repetitive boilerplate code by hand is tedious and error-prone**.

To avoid typing thousands of lines of mechanical assignments, teams built an entire secondary layer of tooling:
- Declarative object mappers and projection libraries,
- Compile-time source generators and AST plugins,
- Builder and factory generators,
- Custom build scripts emitting boilerplate wrappers.

In an agentic workflow, **much of this generative tooling becomes unnecessary overhead**. Coding agents can author, refactor, and update complete, explicit, and fully typed code directly from specifications or schemas. 

What previously required maintaining a specialized compiler plugin or enduring fragile build steps can now be written as plain, readable, ordinary code that is committed directly to source control (see [[Software Engineering May Shift Toward Code Optimized for Agents|code optimized for agents]]).

```text
TRADITIONAL CODEGEN APPROACH:
Domain Models / Schema ──► Compiler Plugin / Mapping Framework ──► Synthetic Hidden Code
                                                                 (Hard to debug, IDE lag)

AGENTIC APPROACH:
Domain Models / Schema ──► Coding Agent ──► Explicit Source Code ──► Normal Compiler & Tests
                                           (Plain, readable, git-tracked, instant debug)
```

## The Inverted Economics of Boilerplate

Historically, software wisdom warned: *"Duplicate code is evil; abstract or generate it."*

That rule made sense because manual developer keystrokes and human maintenance were expensive. If an entity added two fields, updating 30 DTO projections across a codebase was an afternoon of tedious manual work where typos easily caused silent bugs.

AI inverts those economics:

```text
HISTORICAL TRADEOFF:
Cost of manually writing & maintaining 30 explicit mappings
  > Cost of adopting and configuring a code-generator or reflection library

AGENTIC TRADEOFF:
Cost of having an agent author & update 30 explicit mappings ≈ 0
Cost of maintaining a complex generator plugin or configuration DSL > 0
→ Explicit, readable code wins.
```

When an agent can sweep through a codebase and update 20 explicit mapping functions in thirty seconds, you no longer need a complex generator framework just to avoid typing property assignments.

---

## The Hidden Costs of the Codegen Tooling Layer

Maintaining custom source generators and metaprogramming frameworks was never free:

1. **Maintaining Two Codebases Instead of One**: You must maintain your actual application code, plus the generator script, compiler plugin, or mapping DSL.
2. **Fragile Build Pipelines**: Compile-time generators introduce external dependencies, slower build times, and IDE cache synchronization issues where "Go to Definition" leads to temporary, read-only cache directories.
3. **The 80/20 Edge Case Wall**: Generators work smoothly when copying identical fields (`id` $\rightarrow$ `id`). But the moment real business rules show up—formatting a timestamp for a specific timezone, redacting sensitive data, or converting legacy status codes—the generator DSL breaks down. Developers end up inventing convoluted configuration hooks just to handle edge cases.
4. **Debugging Friction**: Stepping through code in a debugger is trivial when the code is plain and explicit. It is painful when execution vanishes into dynamic reflection pipelines or synthetic files that don't map cleanly to source symbols (see [[Hidden Abstractions May Become More Expensive in Agent-Maintained Code]]).

## Plain Explicit Code vs. Opaque Abstractions

Consider how data transformation looks when written explicitly by an agent:

```text
// Plain, explicit projection function generated by the agent:
function project_to_order_summary(order: OrderEntity) -> OrderSummaryDto:
    return OrderSummaryDto(
        order_id = order.id,
        customer_name = order.customer.display_name,
        item_count = len(order.items),
        total_amount = order.total.amount,
        status_label = format_status(order.status),
        created_at_utc = to_utc(order.created_at)
    )
```

This code has clear operational advantages:
- **Zero Hidden Machinery**: No runtime reflection overhead, no heavy runtime library dependencies, and no magic compiler hooks.
- **Direct Compiler and JIT Optimization**: The compiler sees every assignment directly. It can easily inline the function, eliminate dead code, and optimize register usage without fighting dynamic dispatch.
- **Instant Debuggability**: A developer can set a standard breakpoint on any line, inspect values, and step through execution without indirection.
- **Trivial Refactoring**: When the domain entity changes, the developer instructs the agent: *"We split customer name into first and last name. Update all order summary projections and run the test suite."* The agent updates every explicit call site directly.

## Convenience Generators vs. Deep Infrastructure Libraries

Not every generator or library should be replaced with agent-written code. A clear boundary exists between **convenience boilerplate** and **accumulated infrastructure knowledge**:

| Category | Typical Examples | Agentic Approach | Rationale |
| :--- | :--- | :--- | :--- |
| **Convenience Boilerplate** | DTO mappers, builder patterns, API client wrappers, simple CRUD handlers | **Replace with explicit agent code** | Created primarily to save human typing; edge cases are easier to handle in explicit code. |
| **Formal Schema Compilers** | Protobuf, gRPC, OpenAPI client emitters, SQL query compilers | **Keep deterministic generators** | Formal interface schemas require 100% deterministic compilation across multiple programming languages. |
| **Deep Infrastructure** | Serialization engines (JSON/UTF-8), cryptographic libraries, TLS stacks, database storage engines | **Keep trusted third-party packages** | Encode decades of security audits, byte-level optimizations, and tricky edge-case handling that cannot be recreated reliably on the fly. |

The rule of thumb is straightforward:
> If a tool's primary purpose was to save a developer from typing repetitive lines, let the agent write explicit code instead.  
> If a library's value comes from complex algorithms, security hardening, or formal standards compliance, use the established library.

## Keep AI at Development Time, Not in the Build Pipeline

Another critical distinction is where the generation takes place:

```text
BAD PATTERN: RUNNING LLM IN BUILD LOOP
Source Code ──► [Build Command] ──► LLM Call (slow, non-deterministic, network-dependent) ──► Artifact
Result: Fragile builds, broken CI offline, non-reproducible releases.

PROVEN PATTERN: AI AT DEVELOPMENT TIME
Prompt / Spec ──► LLM Agent ──► Explicit Source Code committed to Git ──► Deterministic Compiler ──► Artifact
Result: 100% reproducible builds, instant CI, deterministic testing.
```

An LLM is a probabilistic assistant, not a deterministic compiler step. It belongs in the developer environment where it generates explicit code that is reviewed, tested, and committed to git. Once committed, your normal build toolchain and test runner verify the code deterministically (see [[Testing in the Model, Agent, LLM Era|automated testing harnesses]]).

## Practical Rules for Teams

1. **Prefer explicit functions over complex mapping DSLs**: Let agents generate straightforward, line-by-line conversion functions rather than introducing complex reflection mappers or generator plugins.
2. **Keep the build loop deterministic**: Never invoke language models as an automated step inside continuous integration builds; generate and commit plain code ahead of time.
3. **Don't reinvent infrastructure libraries**: Use agents to write glue code and business logic, but rely on mature, audited packages for serialization, cryptography, and network protocols.
4. **Use tests to catch schema drift**: When relying on explicit mappings instead of compile-time generators, back them up with contract and round-trip unit tests so that missing fields fail loudly in CI.
