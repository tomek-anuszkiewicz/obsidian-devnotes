# Business Logic Is Harder Than Technical Complexity in Agentic Development

When you pair with autonomous coding models, a stark asymmetry quickly becomes obvious: technical infrastructure is remarkably easy for an agent to build, while business logic remains an active minefield.

An agent can spin up a concurrent processing pipeline with exponential backoff, jitter, connection pooling, and OpenTelemetry instrumentation in minutes. The patterns are syntactically complex, but semantically standardized. The agent has parsed millions of public implementations of distributed queues, Redis caches, and database migrations.

In that exact same pull request, the agent can completely butcher a three-line business condition. 

Technical code often carries high syntactic weight but low domain ambiguity. Business logic is the reverse: it often consists of nothing more than a handful of `if` statements, but those statements encode years of historical exceptions, regulatory compromises, accounting boundaries, and unwritten company context.

```
TECHNICAL INFRASTRUCTURE (Syntactically Dense, Semantically Standardized)
  - Concurrent queues, retry pipelines, distributed tracing
  - Connection pools, schema migrations, cache invalidation
  ──► Solved reliably (Standardized patterns across open-source ecosystems)

BUSINESS RULES (Syntactically Simple, Semantically Ambiguous)
  - Accounting settlement boundaries, refund eligibility windows
  - Tax calculation exceptions, legacy customer overrides
  ──► High failure rate (Saturated with unwritten tribal knowledge and domain traps)
```

---

## The Silent Failure Mode: Technically Flawless, Semantically Broken

The most dangerous bug produced by an LLM is never a syntax error, a null dereference, or a broken database query. Compilers, linters, and type checkers catch those before code ever reaches staging.

The real failure mode is code that is:
- Cleanly structured and idiomatic,
- Fully documented,
- Backed by passing unit tests (often generated by the model itself),
- Perfectly sound from an operational and infrastructure standpoint,
- **Fundamentally wrong about the business domain.**

Consider a typical e-commerce or billing workflow. An agent encounters an enum check:

```csharp
PaymentStatus.Paid
```

To an LLM trained on generic web development, `PaymentStatus.Paid` naturally implies that funds have cleared and the transaction is finalized. 

In a real enterprise payment system, `Paid` often merely means the payment gateway successfully placed an authorization hold on the customer's credit card. The actual funds are not captured and settled until an automated clearing batch runs at midnight. 

If the agent writes cancellation logic relying on `PaymentStatus.Paid`, it might block a valid customer cancellation request hours before any settlement occurs. Or worse, if it writes fulfillment logic assuming `Paid` means settled cash, it might release high-value goods before settlement failure alerts can trigger.

The code compiles, runs fast, and passes its tests, yet silently corrupts business operations because the model filled a domain semantic gap with a plausible, generic assumption.

## The Architectural Fix: Decouple Business Decisions from Technical Execution

To work safely with coding agents, you must decouple pure domain decisions from technical side effects and I/O orchestration.

When business rules are tangled with database queries, message queues, and HTTP calls, agents will repeatedly misplace checks, hallucinate state transitions, or bury critical domain rules inside infrastructure boilerplate.

```
┌─────────────────────────────────────────────────────────────┐
│ 1. PURE DECISION COMPONENT (Zero I/O, Zero Side Effects)    │
│    Inputs:  (OrderSnapshot, PaymentSnapshot, DateTimeOffset)│
│    Logic:   Deterministic domain evaluation                 │
│    Output:  Explicit Decision Result (Allowed / Rejected)   │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼ (Decision passed to execution)
┌─────────────────────────────────────────────────────────────┐
│ 2. TECHNICAL EXECUTION (I/O, Transactions, Side Effects)    │
│    - Evaluate returned decision                             │
│    - Commit database transaction                            │
│    - Publish integration events to message broker           │
│    - Emit telemetry and metrics                             │
└─────────────────────────────────────────────────────────────┘
```

### 1. The Pure Decision Component
Isolate business rules into small, deterministic functions that accept state snapshots and return explicit decision models. These components contain no database drivers, no HTTP clients, and no framework abstractions:

```csharp
public CancellationDecision CanCancel(
    OrderSnapshot order,
    PaymentSnapshot payment,
    DateTimeOffset now)
{
    if (order.IsCancelled)
        return CancellationDecision.AlreadyCancelled;

    if (payment.IsIncludedInSettlementBatch)
        return CancellationDecision.PaymentAlreadySettled;

    if (order.IsAlreadyReleased)
        return CancellationDecision.AlreadyReleased;

    return CancellationDecision.Allowed;
}
```

This structural isolation delivers three critical operational advantages:

1. **Instant Human Auditability:** A reviewer can inspect the business policy in fifteen seconds without mentally parsing SQL statements, retry decorators, or serialization logic.
2. **Exhaustive Unit Test Generation:** Because the decision method has zero I/O and zero external dependencies, you can instruct an agent to generate complete truth tables covering every permutation of inputs without mocking a single repository or database connection.
3. **Safe Infrastructure Refactoring:** An agent can rewrite the data access layer, upgrade the ORM, migrate from relational tables to document stores, or swap the message bus without touching the core business invariants.

### 2. The Technical Execution Pipeline
Once the business decision is rendered, surrounding application services handle the necessary I/O, transactional boundaries, and external communications:

```csharp
var decision = cancellationPolicy.CanCancel(
    order,
    payment,
    clock.UtcNow);

if (!decision.IsAllowed)
    return MapFailure(decision);

order.Cancel(userId, clock.UtcNow);

await repository.Save(order, cancellationToken);
await unitOfWork.Commit(cancellationToken);
await eventPublisher.Publish(
    new OrderCancelled(order.Id),
    cancellationToken);
```

By separating evaluation from execution, you restrict the agent's generative power to the areas where it excels: scaffolding plumbing, wiring dependencies, and executing side effects. The business rule itself remains an isolated, tightly guarded domain artifact.

## Preserving Domain Intent with Comments

Modern coding models have an aggressive tendency to refactor code toward standard open-source conventions. If an agent inspects an unusual conditional check, its natural reflex is to simplify, inline, or eliminate the clause to reduce boilerplate.

In an agent-assisted codebase, comments should not explain *what* the code is doing—the code already does that. High-value comments exist to explain *why* the implementation intentionally diverges from standard conventions and *which* obvious refactorings will break production.

```csharp
// A payment may be authorized without being included in a settlement batch.
// Cancellation is blocked only after batch assignment.
// Do not replace this condition with PaymentStatus == Paid.
if (payment.BatchSettlementId is not null)
{
    return CancellationResult.PaymentAlreadySettled;
}
```

This level of commentary provides concrete context windows to an agent:
- It defines the precise operational meaning of the rule.
- It documents why the condition exists despite looking non-standard.
- It explicitly warns the model against a specific, naive simplification that would introduce a silent regression.

### What High-Value Comments Must Convey
Reserve comments for domain reality, not mechanical syntax:
- **Unusual business policies:** Why an edge case is handled counter to common industry standards.
- **Ambiguous state definitions:** What a status field actually represents versus what its name implies.
- **Strict execution sequences:** Why operations must execute in a specific order that a compiler cannot enforce.
- **Historical schema quirks:** Why two seemingly identical columns or status flags must remain separate due to legacy data migrations.
- **Origins of arbitrary constants:** The business or legal justification for timeouts, grace periods, and thresholds.

Noise comments only dilute context:

```csharp
// Save the order.
await repository.Save(order);
```

Mechanical comments waste token space and obscure meaningful intent. 

> **Code explains what happens. Comments explain why it must happen that way.**

## Pragmatic Rules for Agent-Assisted Codebases

1. **Leverage models for infrastructure, verify business logic manually:** Trust agents to configure pipelines, write boilerplate migrations, and wire up telemetry. Never trust them to deduce business policies from generic variable names.
2. **Push domain logic into pure functions:** Keep business calculations free of network calls and database dependencies. If a rule requires I/O, pull the state before running the rule.
3. **Guard non-obvious code paths:** When writing conditions that look inefficient or redundant to a generic parser, write an explicit comment stating why the logic exists and forbidding automated simplification.
4. **Use exhaustive, table-driven tests on decision boundaries:** Lock down domain policies with comprehensive unit test matrices so any semantic drift introduced by an automated refactoring run fails the build instantly.
