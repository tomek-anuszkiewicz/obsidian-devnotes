| **Semantic Locality May Become an Architectural Goal**<br><br>We can think about code as having different levels of semantic locality.<br><br>High semantic locality:<br><br><pre><code>CalculatePrice(order, customer, pricingRules);</code></pre><br><br>The important inputs are visible.<br><br>Lower semantic locality:<br><br><pre><code>priceCalculator.Calculate(order);</code></pre><br><br>The implementation must be discovered.<br><br>Even lower semantic locality:<br><br><pre><code>priceCalculator.Calculate(order);</code></pre><br><br>where dependency injection selects the implementation based on runtime context.<br><br>Very low semantic locality:<br><br><pre><code>priceCalculator.Calculate(order);</code></pre><br><br>where the result also depends on:<br><br><pre><code>current tenant<br>feature flags<br>ambient user<br>interceptors<br>global cache<br>transaction context<br>dynamic configuration</code></pre><br><br>The textual code can remain equally short while the reasoning cost increases dramatically.<br><br>For agent-maintained systems, **semantic locality may become as important as traditional measures such as coupling, cohesion, and duplication**. | **Designing Abstractions for Agent Readability**<br><br>Human-centric API design has historically prioritized terseness:<br><br><pre><code>Minimal lines of code<br>Minimal method parameters<br>Zero boilerplate<br>Aggressive reuse of implicit behaviors</code></pre><br><br>Agent-centric API design shifts those priorities toward clarity and predictability:<br><br><pre><code>Semantic locality over textual brevity<br>Explicit dependencies over ambient context<br>Visible control flow over interceptor chains<br>Mechanically discoverable behavior over convention-based magic<br>Predictable composition over dynamic runtime dispatch</code></pre><br><br>This does not mean code has to become low-level or messy.<br><br><pre><code>.RetryTransient(attempts: 3)</code></pre><br><br>is still an abstraction. It saves a few characters at the cost of hiding every semantic detail an agent needs to know to write safe code.<br><br>> **A well-designed abstraction reduces mechanical syntax without obscuring business semantics.**<br><br>--- |
| **The Likely Direction Is Not "No Abstractions"**<br><br>The more realistic direction is:<br><br><pre><code>hide mechanisms<br>expose semantic decisions<br>centralize implementation<br>localize intent<br>make abstractions inspectable</code></pre><br><br>This could lead to code that is somewhat more verbose than today's most heavily abstracted application architectures.<br><br>But the code may also become:<br><br>&bull; easier for agents to modify,<br><br>&bull; easier for humans to review,<br><br>&bull; easier to test,<br><br>&bull; easier to analyze statically,<br><br>&bull; less dependent on institutional knowledge,<br><br>&bull; safer to refactor automatically.<br><br>The important shift may therefore not be from abstraction to no abstraction.<br><br>It may be from:<br><br><pre><code>implicit, non-local behavior</code></pre><br><br>toward:<br><br><pre><code>explicit, composable, mechanically discoverable behavior</code></pre><br><br>In software increasingly written and maintained by agents, the cost of repetition may fall while the cost of hidden semantics becomes much more visible.<br><br>That could change what we consider "clean" architecture. | **Encoding Business Meaning in the Ubiquitous Vocabulary**<br><br>Semantic locality goes beyond where code physically executes. It also depends heavily on whether the source code uses the exact same concepts and vocabulary as the surrounding domain model, database schema, API contracts, tests, and business documentation.<br><br>Take this routine conditional:<br><br><pre><code>if (payment != null)<br>{<br>    // ...<br>}</code></pre><br><br>In an older codebase, this check might quietly rely on an unwritten convention: *if a payment record exists in this table, it means the invoice has been created but is currently unpaid.*<br><br>A staff engineer who has worked on the billing engine for three years knows that convention by heart. An agent has no way of knowing it. The agent sees a technical null-check:<br><br><pre><code>Payment record exists</code></pre><br><br>From that, it has to guess the underlying business state:<br><br><pre><code>Invoice is unpaid</code></pre><br><br>That inference is fragile. In many cases, the agent will misinterpret the check, assume the payment has already cleared, and write code that introduces subtle accounting bugs.<br><br>Now look at the explicit version:<br><br><pre><code>if (payment.Status == PaymentStatus.Unpaid)<br>{<br>    // ...<br>}</code></pre><br><br>Or better yet:<br><br><pre><code>if (payment.IsUnpaid)<br>{<br>    // ...<br>}</code></pre><br><br>Now the domain concept is stamped directly into the code.<br><br>This becomes especially powerful when the same concept appears across different parts of the system. If the architecture documentation states:<br><br><pre><code>&quot;Retry unpaid payments after 24 hours&quot;</code></pre><br><br>The OpenAPI specification defines:<br><br><pre><code>paymentStatus:<br>  type: string<br>  enum: [unpaid, processing, settled, failed]</code></pre><br><br>And the test suite contains:<br><br><pre><code>[Fact]<br>public async Task ShouldRetryUnpaidPayment_WhenGracePeriodExpires()</code></pre><br><br>An agent searching the repository can instantly and accurately link the documentation, the API spec, the unit tests, and the source code using the shared identifier:<br><br><pre><code>PaymentStatus.Unpaid</code></pre><br><br>That link breaks down completely when business states are hidden behind technical sentinels or indirect object checks:<br><br><pre><code>amount == 0<br>endDate == null<br>retryCount == -1<br>statusCode == 2<br>customerId != null</code></pre><br><br>These raw values usually encode core business rules:<br><br><pre><code>amount == 0            → Plan is free<br>endDate == null        → Subscription is actively running<br>retryCount == -1       → Retry policy is unlimited<br>statusCode == 2        → Transaction is awaiting settlement<br>customerId != null     → Order has an assigned customer profile</code></pre><br><br>Writing code that relies on raw sentinel values forces the agent to constantly infer intent from technical artifacts. A much safer, agent-friendly codebase elevates those technical states into first-class business domain models:<br><br><pre><code>price.IsFree<br>subscription.IsActive<br>retryPolicy.IsUnlimited<br>payment.Status == PaymentStatus.Unpaid<br>order.HasAssignedCustomer</code></pre><br><br>> **Code should express explicit business conclusions, not just raw technical states from which those conclusions must be deduced.**<br><br>This semantic alignment should be consistent across every engineering artifact:<br><br><pre><code>Documentation:<br>    &quot;unpaid payment&quot;<br><br>Domain Code:<br>    PaymentStatus.Unpaid<br><br>API Contract:<br>    paymentStatus: &quot;unpaid&quot;<br><br>Database Schema:<br>    payment_status = &#x27;unpaid&#x27;<br><br>Domain Event:<br>    PaymentMarkedUnpaidIntegrationEvent<br><br>Test Suite:<br>    ShouldRetryUnpaidPayment()</code></pre><br><br>This strict alignment gives an agent distinct advantages:<br><br>&bull; Codebase-wide symbol searches yield precise, relevant hits.<br><br>&bull; Vector embeddings and RAG pipelines retrieve the exact files needed for a task without pulling in irrelevant noise.<br><br>&bull; Translating an issue description or user story into an actionable code modification requires zero guesswork.<br><br>&bull; Code reviews and diff validations become significantly more deterministic.<br><br>&bull; Generated code uses the existing domain language instead of hallucinating parallel concepts.<br><br>Inline comments can help bridge the gap when dealing with legacy systems:<br><br><pre><code>// In the legacy billing system, a non-null payment record indicates an unpaid invoice.<br>if (payment != null)</code></pre><br><br>While useful, comments are fundamentally second-class citizens compared to strongly typed models. It spares human engineers from having to memorize tribal knowledge, and it spares agents from having to make blind guesses about what your code is doing.<br><br>--- |
